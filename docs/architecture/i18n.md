# Internacionalização (i18n)

O Ponto começa como produto brasileiro, mas a arquitetura nasce preparada para vários idiomas. O idioma padrão é **pt-BR**; `en` e `es` já estão habilitados como estrutura.

## Objetivos

- Nenhuma string de interface espalhada pelo código: textos para pessoas vivem em catálogos.
- Chaves tipadas: `t("common.errors.notFoud")` (com erro de digitação) não compila.
- O mesmo mecanismo serve para API, web e mobile, sem acoplar o backend a uma biblioteca de frontend.
- Mensagens de **log não** são traduzidas. Logs são para quem opera o sistema e ficam sempre em inglês.

## O pacote `@ponto/i18n`

```text
packages/i18n/src/
├── locales.ts            SUPPORTED_LOCALES, DEFAULT_LOCALE, tipo Locale
├── negotiate.ts          negotiateLocale(): escolhe o idioma a partir do Accept-Language
├── translator.ts         createTranslator(): devolve a função t()
├── types.ts              MessageKey, Messages, PartialMessages
└── messages/
    ├── index.ts          Registro dos catálogos por idioma
    ├── pt-BR/            Fonte da verdade (catálogo completo)
    │   ├── index.ts
    │   └── common.ts
    ├── en/
    └── es/
```

O pacote não tem dependências e não usa APIs do Node, então funciona em servidor, browser e React Native.

### Catálogos e namespaces

Cada idioma é dividido em **namespaces** (um arquivo por área): `common` hoje, e futuramente `auth`, `posts`, `moderation` etc. As chaves seguem o formato `namespace.grupo.chave`:

```ts
// messages/pt-BR/common.ts
export const common = {
  errors: {
    notFound: "O recurso solicitado não foi encontrado.",
    // ...
  },
}
```

- **pt-BR é a fonte da verdade.** O tipo `MessageKey` é derivado dele, então toda chave precisa existir em pt-BR.
- **Outros idiomas podem ser parciais** (`PartialMessages`). Uma chave sem tradução cai automaticamente para o idioma de fallback (pt-BR). Isso permite lançar uma funcionalidade antes de todas as traduções estarem prontas.
- Hoje os catálogos `en` e `es` traduzem todas as mensagens de `common`, porque são poucas.

### Uso

```ts
import { createTranslator, negotiateLocale } from "@ponto/i18n"

const locale = negotiateLocale(request.headers["accept-language"]) // "pt-BR" | "en" | "es"
const t = createTranslator(locale)

t("common.errors.notFound")
t("posts.errors.editWindowExpired", { minutes: 15 }) // hypothetical key, interpolates {minutes}
```

- `negotiateLocale` respeita pesos (`q=`) do header, casa idioma regional com o base (`en-US` vira `en`, `pt` vira `pt-BR`) e só devolve idiomas habilitados.
- A interpolação usa `{nome}`. Pluralização e formatação de números/datas devem usar `Intl` (`Intl.PluralRules`, `Intl.NumberFormat`, `Intl.DateTimeFormat`) quando forem necessárias.

## Na API

A API traduz apenas o que devolve para pessoas. Hoje isso significa as **mensagens de erro**:

1. O serviço lança `new AppError(ApiErrorCode.RESOURCE_NOT_FOUND)`. Ele não escolhe texto.
2. O `ERROR_CATALOG` liga o código à chave `common.errors.notFound`.
3. O filtro global negocia o idioma pelo `Accept-Language`, limitado a `SUPPORTED_LOCALES`, com fallback em `DEFAULT_LOCALE`.
4. A resposta leva `message` traduzida e o header `Content-Language`.

O `code` (`RESOURCE_NOT_FOUND`) é estável e em inglês; clientes devem tomar decisões pelo código, nunca pelo texto. Clientes que preferirem exibir textos próprios podem traduzir o `code` localmente com o mesmo pacote.

Configuração:

```env
DEFAULT_LOCALE=pt-BR
SUPPORTED_LOCALES=pt-BR,en,es
```

A API não inicia se `DEFAULT_LOCALE` não estiver em `SUPPORTED_LOCALES` ou se houver um idioma desconhecido na lista.

## No web e no mobile

Os apps importam os mesmos catálogos e a mesma função `t()`. Textos de interface comuns aos dois ficam no namespace `app` (`app.tagline`, `app.apiStatus.online`...).

- **Web** (`apps/web/src/lib/i18n.ts`): `getRequestTranslator()` negocia o idioma pelo `Accept-Language` da requisição, no servidor, e o layout define `<html lang>`.
- **Mobile** (`apps/mobile/src/hooks/use-translator.ts`): `useTranslator()` lê os idiomas preferidos do aparelho com `expo-localization`, negocia com `negotiateLocale` e devolve `{ locale, t }`. O hook reage quando a pessoa troca o idioma do sistema.

O idioma escolhido também é enviado à API (`Accept-Language`) pelo `@ponto/api-client`, então as mensagens de erro chegam no mesmo idioma da interface.

Textos que só existem num dos apps (por exemplo, um rótulo específico de gesto no mobile) podem ganhar namespace próprio (`web`, `mobile`) ou ser passados como catálogos extras em `createTranslator(locale, { catalogs })`.

Se no futuro for necessário um recurso que justifique uma biblioteca (por exemplo, ICU MessageFormat completo), os catálogos continuam sendo objetos simples e podem ser carregados por ela sem reescrever as traduções.

## Como adicionar

**Uma mensagem nova:**

1. Adicione a chave em `messages/pt-BR/<namespace>.ts`.
2. Adicione a tradução em `en` e `es`, se já estiver disponível (opcional).
3. Use `t("namespace.grupo.chave")`. O TypeScript valida a chave.

**Um namespace novo:**

1. Crie `messages/pt-BR/<namespace>.ts` e registre em `messages/pt-BR/index.ts`.
2. Faça o mesmo nos outros idiomas quando houver tradução.

**Um idioma novo:**

1. Inclua o código em `SUPPORTED_LOCALES` (`locales.ts`).
2. Crie `messages/<locale>/` e registre o catálogo em `messages/index.ts`.
3. Habilite na API via `SUPPORTED_LOCALES`.
